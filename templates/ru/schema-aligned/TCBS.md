## G3: критерий PASS/FAIL

**PASS:** WRITE–READ BACK–COMPARE совпадает, побочные изменения отсутствуют.

**FAIL / ограничение:** FAIL требует исправления по новому согласованному плану.

| Контроль | Результат |
| --- | --- |
| Структурная проверка | PASS / FAIL / NOT RUN |
| Семантическая проверка REVIEW/HUMAN | PASS / FAIL / NOT RUN |
| Основание, Evidence / locator | _____ |
| Проверяющий и дата | _____ |
| Расхождения и следующий согласованный шаг | _____ |

**Важно:** заполненность формы не доказывает истинность утверждений, достаточность свидетельств или полномочие действовать. UNKNOWN не заменяется догадкой. В BUILD APPROVE означает согласование записи в контекст, не одобрение бизнес-договора.

## Редакционное пояснение к применению

**Протокол G3 (операционная фиксация, без изменения обязательных полей §6.3):** READ исходного состояния → PLAN с идентификатором `approved_plan_id` → явное APPROVE плана записи → WRITE с `write_log` → READ BACK с `readback_snapshot` → COMPARE с `comparison_result` и `diffs`. В журнале необходимо фиксировать разрешённые изменения, прежнее состояние, результат каждой операции и отсутствие побочных изменений. При FAIL запрещена несанкционированная автоматическая коррекция; требуется новый согласованный план. APPROVE разрешает изменение контекстной модели, а не бизнес-действие.

**Решение о нормативной приёмке:** ожидается. Проверки Gate по реальному кейсу не выполнялись.
